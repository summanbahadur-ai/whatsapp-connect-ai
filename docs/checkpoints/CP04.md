## Contract and implementation decisions
- GET /api/auth/csrf -> {token,headerName}; private/no-store; HttpOnly SameSite=Lax
  CSRF cookie. Keep Spring's masked-token handler and CSRF protection enabled.
- POST /api/auth/sign-up/email -> {name,email,password};201 {user}.
- Trim name/email, normalize email case; enforce name/email bounds, minimum8
  password characters and maximum72 UTF-8 bytes for BCrypt. Never trim passwords.
- BCrypt cost12 with {bcrypt} algorithm identifier; no plaintext/reversible storage.
- Explicit auth-role JDBC transaction inserts identity then password credentials.
  Existing identity provisioning trigger creates account/profile/currency defaults.
  Do not also provision in Java. Pipelines are created in their own checkpoint.
- Same-origin frontend sends CSRF header/cookie. Exact configured Origin required
  for signup; default frontend origins localhost/127.0.0.1:3001. No old3000 fallback.
- Safe errors:400 invalid input,403 security rejection,409 duplicate email,
  503 storage failure. Never return passwords, hashes, SQL or exception details.
- CP04 creates an account but does not auto-login. Preserve signup layout and show
  completion. Sign-in/session remains CP05; invitations remain their own module.
- No schema change is expected: accepted identity/domain tables already support this.
  Add a new migration and refresh main SQL only if a structural change is needed.

No new SQL file needs executing. To inspect records in pgAdmin Query Tool on
whatsapp_connect_ai, use this read-only query (it does not display password hashes):

```sql
SELECT u.id, u.name, u.email, u.email_verified,
       p.account_role, a.name AS account_name, a.default_currency,
       EXISTS (
         SELECT 1 FROM identity.password_credentials c WHERE c.user_id = u.id
       ) AS has_password_credential
FROM identity.users u
JOIN public.profiles p ON p.user_id = u.id
JOIN public.accounts a ON a.id = p.account_id
ORDER BY u.created_at DESC;
```
